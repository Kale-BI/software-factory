The factory running · 01

Triage, and the morning report

Delegate a Backlog ticket and Symphony triages it within the minute, attempting the one thing that reveals what the ticket actually needs: the full AFK brief. The human wakes up to a one-glance board report, not a pile.

Brief-first, not score-first

Most triage classifies a ticket as written: read it, guess its size, guess its risk, file it. Ours classifies by drafting. The session always attempts the complete brief — the contract an unattended agent would need: deliverable, validation gate, plan — and the route falls out of where the draft fails. Entanglement between decisions only shows up when you try to write their option lists; scoring never finds it.

Before drafting, every open question on the ticket is classified by who holds the answer:

  • Fact — the world holds it (API capability, library behaviour, existing code). Looked up during triage, against primary sources, and cited in the brief.
  • Preference — the maintainer holds it. Carried forward to routing.
  • Empirical — nobody holds it yet. A prototype answers it.
The discipline: a question answerable from documentation that reaches a human is a triage bug — the maintainer's attention was spent to save the agent a lookup.

Four routes, rendered as columns

A route is a claim about what the ticket waits for — never about what anyone is currently doing to it. On Kale's board each route is a state, so the board itself shows what every ticket awaits; there are no triage labels. Untriaged work sits in Backlog.

Delegating in Backlog is consent for the whole ride: a ticket that triages clean proceeds through implementation to Human Review, where the evidence contract is the gate. Resuming a parked ticket is one drag — answer the card or hold the session, then move it to Backlog (re-triage reads the reply) or straight to Todo. Ties break toward grilling: a wrongly-carded ticket gets built confidently wrong, which costs more than a session.

The closed-form test

A blank in the brief qualifies for a decision card only if all five hold. Fail any one and the ticket goes to grilling instead:

01Enumerable.You can list 2–4 options and would execute any of them verbatim, happily. Prose options for a visual question fail this; a variants prototype makes them pass.
02Independent.The answer leaves every other blank's options unchanged.
03Named.Every term the question leans on has one settled meaning in the project's domain model. When different readings of a term produce different tickets, the vocabulary needs a session before the decision does.
04Few.At most two blanks on the ticket. More is a conversation wearing a form's clothes.
05Recoverable.A wrong pick is cheap to reverse. Schema migrations, public API shapes, pricing go to grilling even as a single clean question — the point is stress-testing the reasoning, not picking.

Prototypes, during triage

A visual blank — "which direction should this UI take" — can never be honestly enumerated in prose. So the triage session builds a throwaway variants prototype on the spot: one self-contained HTML file, two to four distinct directions behind a control bar. The blank becomes genuinely closed-form, and the decision card links the prototype as its options. Behavioural tangles get a clickable logic walkthrough attached to the grilling agenda as session material. Both are disposable by construction: zero setup, state in memory, dead once the verdict is recorded — and yes, the unattended run builds them too: the prototype exists precisely because nobody with taste is present, so taste can be exercised later in one reply.

Where the words go

The ticket's content — draft brief, and later the spec that supersedes it — lives at the effort's long-form home, one HTML document per effort in the dossiers site, created lazily and linked from the ticket. The ticket description stays its author's; the comment stays a glance. Every comment the session posts opens with "Generated by AI during triage." — a stranger reading the tracker always knows which voice is speaking.

The morning report

Every morning at 07:30 London time, a scheduler on an always-on machine fires one script. It is read-only: one query over the full board, one Slack message — one line per ticket with its link, grouped by what it awaits (Awaiting you / In flight / Backlog, untriaged), with tickets quiet for three days flagged. It launches no sessions and writes nothing to the tracker, so it photographs outcomes rather than promising them. Reply in the thread with an answer for a ticket and the team agent does the drag for you: your reply lands on the ticket, the ticket returns to Backlog, and the triage lane reads it.

The principle underneath: runners launch sessions, reporters read state. The report and the triage that feeds it share no machinery — which is why the report can never claim something happened that didn't.

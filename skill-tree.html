The skill tree

Twenty skills run the machine. Each one is here because something in the system references it — and for no other reason.

Admission by reference

The tree had grown to twenty-eight skills, and a census showed what growth without a rule produces: six skills nothing referenced anywhere, one vendored skill accounting for 61% of the repo's lines with no in-repo dependents, three manifest rows pointing at folders deleted weeks earlier. Nothing was wrong with any individual skill. What was missing was a test for whether a skill belongs.

The test is mechanical: a skill lives in the tree if, and only if, something in the system references it — another skill, a seeded doc, a runner's prompt, or a cron. A skill that is merely useful goes to a personal library instead. Usefulness is not membership, and "we might want it someday" is the exact argument the rule exists to refuse. Applying it cut the tree to twenty-two, and the version after that to twenty.

The seam rule

Every fact a skill needs is placed by where it varies. Varies per repo → a seeded doc in that repo, written by the setup skill. Shared across the org → a reference skill. Varies per machine or runner → the runtime that owns it, whether that is a dispatcher's config or a personal agent library. Skills are interfaces; a skill carrying a fact from the wrong class is misplaced configuration wearing a skill's clothes. The reference class is the narrowest of the four, and it has since shrunk to one member — see below.

The rule predicts things. When the stuck column was renamed on the board, the rename touched four repos' configuration files and zero skills — exactly what placement-by-variance says should happen, because a column's name varies per tracker and no skill should ever have held it.

What the cut taught

  • Two "unused" skills were kept and wired instead of killed — they were unreferenced, but the reference was genuinely missing rather than the skill: implement now calls the debugging skill when a failure resists explanation, and ship calls the merge-conflict skill when a merge conflicts.
  • One skill was born from the cut: brief, the reference skill owning the agent-ready contract that three other skills had each been restating. One responsibility, one home.
  • One skill was reclassified rather than moved: evidence looked like a helper, but it was made a spine stage between implement and human review, on the argument that the judge should sit outside the system under test.

The last two turned out to be the same mistake, and the next version undid both.

What version four corrected

Three faults traced back to one cause. Unattended runs stalled on tickets carrying no plan and none of the facts triage had verified. Grilling sessions jumped straight to specs, because the placement rule in writing-for-humans redefined a grilling session's output as a brief. And repos accumulated an effort-agnostic decisions file that grew without bound, because it was the only home a grilling record had. In each case a Kale-wide doctrine sat in a reference skill that every session re-read, and the indirection through $brief and $writing-for-humans quietly changed what the calling skill meant.

So the doctrine moved to where it is read once: the files the setup skill seeds into each repo. The tracker instructions now carry how to write on that tracker and what a ready ticket contains — the five evidence kinds and the follow-up shape included — and a new artefact document names where the effort's long-form record lives, seeded from three hosts: a file in the repo, a Claude artefact, a published site. Every engineering skill opens with one sentence pointing at the tracker instructions, and the flow skills shrank below their upstream size while the seeds grew.

Evidence did not stop existing; it stopped being a skill. It is the closing paragraph of implement, produced in a sub-agent with fresh context that was not part of the session that wrote the code — which is what "the judge sits outside the system under test" always required. A separate context, not a separate skill.

The quiet rule underneath: the tree is derived from the process, so its size is a consequence, not a target. If the process grows a stage, the tree grows a skill; nothing else grows it.
